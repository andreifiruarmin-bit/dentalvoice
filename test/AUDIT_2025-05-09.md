## 1. ARCHITECTURE OVERVIEW (Prezentare Generală)

### 1.1 Frontend Architecture
- **Framework:** React 19 + TypeScript 5.8 + Vite 6.2
- **Styling:** Tailwind CSS 4.1.14 + Framer Motion (motion 12.23.24)
- **Icons:** Lucide React 0.546.0
- **Routing:** React Router DOM 7.14.0
- **State:** Local component state (no global state manager)
- **Auth:** Supabase Auth (email/password) with JWT tokens

**Key Components:**
- `ClinicDashboard.tsx` (75KB) - Main receptionist dashboard with 4 tabs: Calendar, Appointments, Patients, Settings
- `ChatWidget.tsx` (34KB) - Embeddable WebBot for patient self-service booking
- `LandingPage.tsx` (40KB) - Marketing site with SEO/GEO optimization
- `EmbedChatPage.tsx` - Public embed route (no auth required)
- `SettingsSection.tsx` (64KB) - Clinic configuration UI (password-protected: admin/admin)

**Component Architecture:**
```
src/components/
├── CalendarViews/
│   ├── DayView.tsx      - Hourly grid (09:00-18:00)
│   ├── WeekView.tsx     - 7-day grid (default view)
│   └── MonthView.tsx    - Calendar with appointment counts
├── AppointmentsList.tsx - Filterable list with pagination
├── BlockDoctorModal.tsx - Manual slot blocking
├── EditBlockedSlotModal.tsx - Vacation/concediu management
├── PatientsSection.tsx  - Patient search & management
├── UnlockSlotModal.tsx  - Manual slot release
├── ChatWidget.tsx       - WebBot widget (public)
├── FloatingHub.tsx      - Action buttons
└── SettingsSection.tsx  - Doctors/Services/Holidays/Reminders config
```

### 1.2 Backend Architecture
- **Runtime:** Node.js + Express 4.21.2
- **Deployment:** Vercel Serverless Functions
- **Entry Point:** `api/index.ts` (2,076 lines, 58 route handlers)

**Module Structure:**
```
api/
├── index.ts              - Route definitions only
├── lib/
│   ├── shared.ts         - Config, Supabase client, utilities (812 lines)
│   ├── booking.ts        - Core booking engine (761 lines)
```

**Authentication Layers:**
1. **Public Routes:** `/api/webhook/whatsapp`, `/api/leads`, `/widget.js`, `/embed/*`
2. **JWT Protected (Dashboard):** `verifySupabaseJWT` middleware - validates Supabase tokens via `supabaseAdmin.auth.getUser(token)`
3. **API Key Protected (Legacy/Internal):** `protectRoute` middleware - checks `x-api-key` against `ADMIN_API_KEY`
4. **Cron Protected:** `protectCron` middleware - checks `x-cron-secret` against `CRON_SECRET`

### 3.3 Multi-Clinic Readiness Assessment

**To onboard a second clinic today, the following changes are needed:**

1. **Database Records Required:**
   - Insert row into `doctors` table with new `clinic_id`
   - Insert rows into `services` table with new `clinic_id`
   - Insert rows into `clinic_config` with new `clinic_id`
   - Create Supabase Auth user + insert into `clinic_users` mapping table

2. **Environment Variables (per deployment):**
   - `CLINIC_ID=new-clinic-slug` (unique per clinic)
   - `SUPABASE_*` (same DB, different isolation via clinic_id)
   - `SMTP_*` (can share or be clinic-specific)
   - `CRON_SECRET` (shared)

3. **Vercel Deployment:**
   - Create new Vercel project OR use same project with environment-specific vars
   - Each clinic needs separate deployment (current design = single-tenant per deployment)

4. **Hardcoded References to Change:**
   - None critical - all use `getClinicId()`
   - Default fallback values in `shared.ts` use env vars which would be clinic-specific

**Current Multi-Tenancy Model:** Single-tenant per deployment (isolation via env var + DB filtering). This is CORRECT for SaaS - each clinic gets own Vercel deployment.
